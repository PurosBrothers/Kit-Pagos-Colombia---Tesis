3.1 · El problema

La misma intención de cobro. Dos mundos incompatibles.

Sin una capa de abstracción, integrar Wompi y Mercado Pago para cobrar $150.000 COP con tarjeta exige dos modelos incompatibles. Nadie tiene que leer todo el código para ver que no se parecen en nada.

Wompi nativo

2 llamadas HTTP · Monto en centavos · Firma SHA-256
wompi-pago-tarjeta.ts

Mercado Pago nativo

1 llamada HTTP · Monto en pesos · Idempotencia obligatoria
mercadopago-pago-tarjeta.ts

Análisis técnico de disparidades encontradas

Monto y divisa
Wompi exige montos expresados como enteros en céntimos (15000000). Mercado Pago y Kushki exigen pesos enteros (150000). Una confusión en esta regla produce cobros multiplicados o divididos por 100.
Cabeceras y firmas
Wompi rechaza la petición con HTTP 422 si falta la firma SHA-256 calculada con el secreto de integridad. Mercado Pago devuelve HTTP 400 si se omite la cabecera X-Idempotency-Key (UUID v4 generado por petición).
Flujo previo
Wompi exige obtener un token de aceptación de términos consumido en una llamada GET previa al endpoint de merchant; Mercado Pago procesa directo pero rechaza con error si no se envía installments: 1 como entero explícito.

3.3 · Arquitectura del artefacto

El artefacto son tres cosas, no una

Reducir el proyecto al SDK pierde de vista la mitad del valor técnico. Los tres componentes resuelven la integración completa, desde el diseño de software hasta las pruebas automatizadas sin credenciales.

01

SDK Hexagonal

Paquete npm con tipado TypeScript estricto. Aísla las reglas de negocio de los detalles de HTTP o librerías de terceros. Incluye el módulo kit-pagos-colombia/browser para tokenizar tarjetas directamente en el navegador sin exponer el backend a PCI DSS.

TypeScript 5.x · Arquitectura Hexagonal · Zero Node Dependencies · Módulo /browser
02

API de Simulación

Servidor local con 23 rutas simuladas para ejercitar los flujos que los sandboxes reales bloquean (como el desenlace de PSE o la Orders API de Mercado Pago). Expone además la capa REST en /v1/api para probar cobros sin escribir código.

23 Rutas Mock · Capa REST /v1/api · Sin Costo / Sin Red · Respuestas Predecibles
03

Documentación de Datos

El componente más subestimado y el que más tiempo ahorra. Documenta las tarjetas de prueba, bancos de PSE, llaves públicas y particularidades medidas contra los entornos reales de cada proveedor para evitar horas de depuración a ciegas.

3.4 · Límites explícitos

Lo que el proyecto no hace

Esta sección separa un trabajo de grado riguroso de una promesa publicitaria. Los límites están deliberadamente acotados para garantizar integridad arquitectónica y verificabilidad empírica.

01

Los códigos de banco de PSE no son universales

Cada pasarela utiliza sus propios códigos para la lista de bancos (en Mercado Pago Bancolombia es 1007; en Rapyd es co_pse_bancolombia_bank). El SDK unifica el método getPseBanks() y traduce el estándar PseBankCode.BANCOLOMBIA, pero los bancos simulados dependen de cada pasarela.

02

El token de tarjeta no es portable entre pasarelas

Un token emitido contra Wompi no puede ser cobrado en Mercado Pago ni en Kushki. La tokenización la realiza el frontend (vía kit-pagos-colombia/browser o librería oficial) contra la pasarela activa seleccionada por el comercio.

03

Solo Tarjeta de Crédito/Débito y PSE

El alcance formal unifica los dos métodos de pago mayoritarios del comercio digital en Colombia. No contempla pagos en efectivo (Efecty, Baloto), billeteras móviles directas (Nequi, Daviplata), suscripciones recurrentes ni dispersión de fondos.

04

La redirección bancaria no desaparece

PSE redirige obligatoriamente al usuario al portal de su banco en las cuatro pasarelas. El SDK normaliza cómo se solicita el pago y cómo se recibe la URL de retorno, pero no elimina el paso de autorización bancaria externa.

Descargo sobre métricas y beneficios comparativos: Cualquier afirmación sobre "ahorro del 80% en tiempo de integración" o "reducción de líneas de código" no se publica aquí porque no está inventada. Esas cifras las producirá formalmente el experimento empírico con desarrolladores en la Fase 5 del proyecto de tesis.
3.5 · Guía de inicio

Comenzar a probar en 30 segundos

La vía más corta para evaluar el Kit Pagos es la capa REST: una sola petición HTTP sin instalar Node ni compilar proyectos. Para integración en código fuente, el paquete npm está estructurado.

1. Probar con una petición HTTP (Capa REST)

La vía más rápida

La API de Simulación expone el SDK a través de una interfaz REST en /v1/api. Permite ejecutar cobros y recibir respuestas normalizadas usando únicamente curl o Postman.

curl -X POST /v1/api/payments
  1. a Descubre las pasarelas activas con GET https://kit-pagos-colombia.onrender.com/v1/api/gateways (o en local con localhost:3000).
  2. b Cambia el campo gateway por wompi, kushki o rapyd para observar cómo cada una responde con su estado canónico.

2. Integrar en tu proyecto Node / TypeScript

Paquete npm oficial

Instala el SDK para utilizar las clases de dominio, objetos de valor inmutables, adaptadores y validación de tipos estricta.

Terminal 
npm install kit-pagos-colombia
Clonar el monorepositorio localmente:
Instalación completa 
# Compilar SDK y levantar API de simulación
cd sdk && npm install && npm run build
cd ../simulator-api && npm install && npm run dev

# Ejecutar los ejemplos ejecutables
cd ../examples && npm install && npm run simulate:wompi
Consulta la Guía de Implementación completa ↗ para el detalle paso a paso de cada caso de uso.
