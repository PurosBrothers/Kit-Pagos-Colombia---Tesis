3.1 · El problema

La fragmentación de pagos en Colombia: contratos incompatibles y reglas dispersas.

Sin una capa de abstracción, integrar Wompi, Mercado Pago, Kushki y Rapyd para procesar cobros en Colombia exige lidiar con dialectos técnicos completamente asimétricos. La disparidad abarca desde la escala monetaria hasta los mecanismos criptográficos de verificación.

Cuatro disparidades estructurales encontradas en sandboxes colombianos

1. Escala y divisa
Wompi exige montos expresados como enteros en céntimos (15000000). Mercado Pago y Kushki exigen pesos enteros (150000). Un error en esta regla produce cobros multiplicados o divididos por 100 en producción.
2. Firmas y seguridad
Wompi rechaza la petición con HTTP 422 si falta la firma SHA-256 calculada con el secreto de integridad. Rapyd exige firma HMAC-SHA256 combinando ruta, timestamp, salt y access_key. Mercado Pago exige la cabecera X-Idempotency-Key (UUID v4) por petición.
3. Asimetría en PSE
Cada pasarela maneja códigos de banco propietarios (en Mercado Pago Bancolombia es 1007; en Rapyd es co_pse_bancolombia_bank). Wompi entrega la URL de redirección bancaria síncronamente, mientras Kushki exige dos llamadas ("Transfer In") y Mercado Pago requiere órdenes previas.
4. Bloqueos en pruebas
La Orders API de Mercado Pago para PSE responde HTTP 401 en sandbox exigiendo credenciales de producción. Kushki no implementa consulta de estado de tarjeta en su API oficial (responde CAS004). El SDK desacopla estas fallas con la API de Simulación.

Comparación nativa: la misma intención de cobro, dos mundos incompatibles

Observe cómo Wompi exige dos llamadas HTTP, cálculo manual de firma SHA-256 y montos en centavos, mientras Mercado Pago requiere cabecera de idempotencia obligatoria y montos en pesos.

Wompi nativo

2 llamadas HTTP · Monto en centavos · Firma SHA-256
wompi-pago-tarjeta.ts 
// 1. Obtener acceptance_token obligatorio previo
const presign = await fetch("https://sandbox.wompi.co/v1/merchants/pub_test_x");
const { presigned_acceptance } = (await presign.json()).data;
const token = presigned_acceptance.acceptance_token;

// 2. Calcular firma de integridad SHA-256 en centavos
const raw = "ORD-1" + "15000000" + "COP" + "integrity_secret";
const signature = sha256(raw);

// 3. Petición POST a Wompi
const res = await fetch("https://sandbox.wompi.co/v1/transactions", {
  method: "POST",
  headers: { Authorization: "Bearer pub_test_x" },
  body: JSON.stringify({
    amount_in_cents: 15000000, // <- Centavos obligatorios
    currency: "COP",
    signature,
    acceptance_token: token,
    payment_method: { type: "CARD", token: "tok_test_card" },
    reference: "ORD-1",
  }),
});

Mercado Pago nativo

1 llamada HTTP · Monto en pesos · Idempotencia obligatoria
mercadopago-pago-tarjeta.ts 
// Cobro directo en Mercado Pago (sin acceptance_token)
// Exige cabecera X-Idempotency-Key y monto en pesos
const idempotencyKey = crypto.randomUUID();

const res = await fetch("https://api.mercadopago.com/v1/payments", {
  method: "POST",
  headers: {
    Authorization: "Bearer APP_USR-xxx",
    "X-Idempotency-Key": idempotencyKey, // <- Cabecera obligatoria
  },
  body: JSON.stringify({
    transaction_amount: 150000, // <- Pesos directos (no centavos)
    token: "tok_test_card",
    installments: 1, // <- Obligatorio como entero
    payer: { email: "cliente@example.com" },
    external_reference: "ORD-1",
  }),
});

El mismo cobro unificado: una sola línea distinta

Con Kit Pagos Colombia, el código de cobro permanece inalterado. El cambio de proveedor es una decisión de configuración en una única propiedad del adaptador.

cobro-unificado.ts 
import {
  KitPagos,
  Gateway,
  Amount,
  Currency,
  OrderReference,
  Payer,
  PaymentMethod,
} from "kit-pagos-colombia";

// 1. Instanciar pasarela activa (lo único que cambia para alternar)
const kitPagos = new KitPagos({
  gateway: Gateway.WOMPI, // <- Lo único que cambia para alternar
  credentials: {
    [Gateway.WOMPI]: {
      publicKey: "pub_test_demo",
      privateKey: "prv_test_demo",
      integritySecret: "test_integrity_secret",
    },
  },
});

// 2. Cobro unificado: idéntico para cualquier pasarela
const resultado = await kitPagos.createPayment({
  amount: new Amount("150000.00"),
  currency: new Currency("COP"),
  orderReference: new OrderReference("ORDER-1042"),
  payer: new Payer({
    email: "cliente@example.com",
    fullName: "Jaime Pavlich",
  }),
  paymentMethod: PaymentMethod.card("tok_test_card_12345"),
});

Particularidad de Rapyd: En Rapyd, el estado de éxito nativo es CLO. No significa "pagado" sino "cerrado" (closed). El adaptador evalúa CLO en conjunto con el flag booleano paid: true para emitir APPROVED de forma determinista.

Tokenización en el navegador: cumplimiento PCI DSS con KitPagosBrowser

Por normativa internacional (PCI DSS), el backend del comercio jamás debe recibir números de tarjeta en texto plano. El submódulo kit-pagos-colombia/browser (14 KB, cero dependencias) tokeniza directamente desde el cliente web contra Wompi o Mercado Pago y retorna un token opaco seguro (tok_...) para que su servidor procese el cobro sin exponerse a cargas regulatorias.

tokenizar-tarjeta-browser.ts 
import { KitPagosBrowser, Gateway } from "kit-pagos-colombia/browser";

const browser = new KitPagosBrowser();

// Tokenización directa en navegador: el número de tarjeta jamás toca tu backend (PCI DSS)
const { token } = await browser.tokenizeCard({
  gateway: Gateway.WOMPI,
  publicKey: "pub_test_demo",
  card: {
    number: "4242424242424242",
    cvc: "123",
    expMonth: "12",
    expYear: "28",
    cardHolder: "Jaime Pavlich",
  },
});

3.4 · Límites explícitos

Lo que el proyecto no hace

Esta sección separa un trabajo de grado riguroso de una promesa publicitaria. Los límites están deliberadamente acotados para garantizar integridad arquitectónica y verificabilidad empírica.

01

Los códigos de banco de PSE no son universales

Cada pasarela utiliza sus propios códigos para la lista de bancos (en Mercado Pago Bancolombia es 1007; en Rapyd es co_pse_bancolombia_bank). El SDK unifica el método getPseBanks() y traduce el estándar PseBankCode.BANCOLOMBIA, pero los bancos simulados dependen de cada pasarela.

02

El token de tarjeta no es portable entre pasarelas

Un token emitido contra Wompi no puede ser cobrado en Mercado Pago ni en Kushki. La tokenización la realiza el frontend (vía kit-pagos-colombia/browser o librería oficial) contra la pasarela activa seleccionada por el comercio.

03

Solo Tarjeta de Crédito/Débito y PSE

El alcance formal unifica los dos métodos de pago mayoritarios del comercio digital en Colombia. No contempla pagos en efectivo (Efecty, Baloto), billeteras móviles directas (Nequi, Daviplata), suscripciones recurrentes ni dispersión de fondos.

04

La redirección bancaria no desaparece

PSE redirige obligatoriamente al usuario al portal de su banco en las cuatro pasarelas. El SDK normaliza cómo se solicita el pago y cómo se recibe la URL de retorno, pero no elimina el paso de autorización bancaria externa.

Descargo sobre métricas y beneficios comparativos: Cualquier afirmación sobre "ahorro del 80% en tiempo de integración" o "reducción de líneas de código" no se publica aquí porque no está inventada. Esas cifras las producirá formalmente el experimento empírico con desarrolladores en la Fase 5 del proyecto de tesis.
