3.1 · El problema

Integrar pasarelas en Colombia es lidiar con cuatro mundos distintos

Cada pasarela diseñó su API con convenciones incompatibles: unas piden centavos y otras pesos; unas exigen SHA-256 en el payload y otras HMAC en headers; y en PSE cada una maneja códigos de banco propietarios. Si integras directo, tu lógica de negocio se llena de condicionales por pasarela.

Cuatro diferencias críticas que encontramos probando contra sandboxes reales

1. Escala y divisa
Wompi pide centavos enteros (15000000 para $150.000 COP). Mercado Pago y Kushki piden pesos (150000). Un error acá te cobra 100 veces más o 100 veces menos en producción.
2. Firmas y seguridad
Wompi responde HTTP 422 si no calculas la firma SHA-256 con tu secreto de integridad. Rapyd pide firma HMAC-SHA256 combinando ruta, timestamp, salt y access_key. Mercado Pago exige una cabecera X-Idempotency-Key (UUID v4) por petición.
3. Asimetría en PSE
Bancolombia en Mercado Pago es el código 1007; en Rapyd es co_pse_bancolombia_bank. Además, Wompi no entrega la URL del banco al crear el cobro: aparece en una consulta posterior, junto con el desenlace; y Kushki exige dos llamadas obligatorias (crear token y luego transfer-in).
4. Bloqueos en pruebas
La Orders API de Mercado Pago, la del PSE, responde HTTP 401 a las credenciales TEST-; solo sirve el par de prueba de un vendedor de prueba. Kushki responde CAS004 al consultar el estado de una tarjeta. Para no quedarnos varados en desarrollo, construimos el simulador local.

Lo que encontramos en los sandboxes: límites de las pasarelas, no del SDK

Mercado Pago · credenciales
Las de prueba son el par APP_USR- de «Credenciales de prueba» de una aplicación de Checkout API vía Orders. Un par TEST- recibe 401 en la Orders API, y el APP_USR- de producción cobra dinero real.
Mercado Pago · túnel
El PSE no vuelve a localhost: rechaza una URL de retorno local. Para probarlo en la máquina hay que servir la página por un túnel público, y la API detrás de un proxy tiene que leer la IP del pagador de X-Forwarded-For.
Kushki · PSE en UAT
La página del banco y la vuelta funcionan, pero la transferencia se queda en initializedTransaction: Kushki activa la simulación de estados por comercio, y hay que pedírsela.
Kushki · tarjeta
El token queda atado al monto del cobro: cobrarlo por otro responde 400 K220. La tarjeta que su documentación lista como aprobada no siempre tokeniza en la cuenta de prueba.
Rapyd · bancos PSE
El sandbox solo cobra 9 de sus 50 bancos, y el catálogo no dice cuáles; además renombra métodos sin aviso. El SDK devuelve solo los que cobran.
Rapyd · tarjeta
No hay token en el navegador: la tarjeta se escribe en su página alojada, que pasa por un simulador de 3DS y devuelve al comercio. El SDK lo entrega como una redirección, igual que un PSE.
Wompi · PSE
El sandbox no tiene página de banco: el desenlace se elige con tres bancos de prueba, el que aprueba, el que declina y el que simula un error.
Llaves del navegador
La llave pública con la que la página tokeniza tiene que ser del mismo par que las credenciales con que el servidor cobra: si son de cuentas distintas, el token no sirve.

Misma intención de cobro, dos implementaciones incompatibles

Para cobrar una tarjeta en Wompi necesitas dos llamadas HTTP, calcular una firma SHA-256 a mano y pasar el monto en centavos. En Mercado Pago es una sola llamada, pero exige pesos directos y una cabecera de idempotencia UUID v4 obligatoria.

Wompi nativo

2 llamadas HTTP · Monto en centavos · Firma SHA-256
wompi-pago-tarjeta.ts 
// 1. Obtener acceptance_token obligatorio previo
const presign = await fetch("https://sandbox.wompi.co/v1/merchants/pub_test_x");
const { presigned_acceptance } = (await presign.json()).data;
const token = presigned_acceptance.acceptance_token;

// 2. Calcular firma de integridad SHA-256 en centavos
const raw = "ORD-1" + "15000000" + "COP" + "integrity_secret";
const signature = sha256(raw);

// 3. Petición POST a Wompi
const res = await fetch("https://sandbox.wompi.co/v1/transactions", {
  method: "POST",
  headers: { Authorization: "Bearer pub_test_x" },
  body: JSON.stringify({
    amount_in_cents: 15000000, // <- Centavos obligatorios
    currency: "COP",
    signature,
    acceptance_token: token,
    payment_method: { type: "CARD", token: "tok_test_card" },
    reference: "ORD-1",
  }),
});

Mercado Pago nativo

1 llamada HTTP · Monto en pesos · Idempotencia obligatoria
mercadopago-pago-tarjeta.ts 
// Cobro directo en Mercado Pago (sin acceptance_token)
// Exige cabecera X-Idempotency-Key y monto en pesos
const idempotencyKey = crypto.randomUUID();

const res = await fetch("https://api.mercadopago.com/v1/payments", {
  method: "POST",
  headers: {
    Authorization: "Bearer APP_USR-xxx",
    "X-Idempotency-Key": idempotencyKey, // <- Cabecera obligatoria
  },
  body: JSON.stringify({
    transaction_amount: 150000, // <- Pesos directos (no centavos)
    token: "tok_test_card",
    installments: 1, // <- Obligatorio como entero
    payer: { email: "cliente@example.com" },
    external_reference: "ORD-1",
  }),
});

Con Kit Pagos: el mismo cobro, solo cambias la pasarela

El código del cobro es exactamente el mismo sin importar quién procese la transacción. Si mañana cambias de proveedor o agregas uno nuevo, tu lógica de pagos no cambia.

cobro-unificado.ts 
import {
  KitPagos,
  Gateway,
  Amount,
  Currency,
  OrderReference,
  Payer,
  PaymentMethod,
} from "kit-pagos-colombia";

// 1. Instanciar pasarela activa (lo único que cambia para alternar)
const kitPagos = new KitPagos({
  gateway: Gateway.WOMPI, // <- Lo único que cambia para alternar
  credentials: {
    [Gateway.WOMPI]: {
      publicKey: "pub_test_demo",
      privateKey: "prv_test_demo",
      integritySecret: "test_integrity_secret",
    },
  },
});

// 2. Cobro unificado: idéntico para cualquier pasarela
const resultado = await kitPagos.createPayment({
  amount: new Amount("150000.00"),
  currency: new Currency("COP"),
  orderReference: new OrderReference("ORDER-1042"),
  payer: new Payer({
    email: "cliente@example.com",
    fullName: "Jaime Pavlich",
  }),
  paymentMethod: PaymentMethod.card("tok_test_card_12345"),
});

El caso de Rapyd: En Rapyd el estado de éxito es CLO, que significa "cerrado" (closed), no pagado. Un pago cancelado o vencido también puede quedar en CLO. El adaptador verifica que venga CLO junto con paid: true para confirmar que la transacción realmente se aprobó.

Tokenización en el cliente: cumplimiento PCI DSS

El número de la tarjeta no pasa por tu servidor: el navegador lo manda directo a la pasarela, y tu backend solo recibe el token. El módulo kit-pagos-colombia/browser (22 KB, cero dependencias) tokeniza directo desde el navegador contra Wompi, Mercado Pago o, desde la 0.6.0, Kushki, y te entrega un token opaco listo para cobrar desde el backend. Rapyd no tokeniza en el navegador: el pago se crea sin token y el pagador escribe la tarjeta en su página alojada.

tokenizar-tarjeta-browser.ts 
import { KitPagosBrowser, Gateway } from "kit-pagos-colombia/browser";

const browser = new KitPagosBrowser();

// Tokenización directa en navegador: el número de tarjeta jamás toca tu backend (PCI DSS)
const { token } = await browser.tokenizeCard({
  gateway: Gateway.WOMPI,
  publicKey: "pub_test_demo",
  card: {
    number: "4242424242424242",
    cvc: "123",
    expMonth: "12",
    expYear: "28",
    cardHolder: "Jaime Pavlich",
  },
});

3.3 · Arquitectura

El proyecto son tres piezas, no solo el SDK

Hacer solo una librería de TypeScript no resolvía el problema real. Para integrar pasarelas en Colombia necesitas tres cosas: el SDK para tu código, un simulador para no depender de sandboxes inestables, y datos de prueba reales para no perder horas adivinando qué tarjeta pasa en cada una.

01

SDK Hexagonal

Paquete npm en TypeScript con tipado estricto y una sola dependencia de runtime (big.js). El dominio no sabe nada de HTTP ni de pasarelas específicas. Incluye kit-pagos-colombia/browser para tokenizar tarjetas en el front sin meter tu backend en alcance PCI DSS.

TypeScript 6 · Arquitectura Hexagonal · Una Dependencia (big.js) · Módulo /browser
02

API de Simulación

Servidor local con 33 rutas mock para flujos de tarjeta y PSE de Wompi, Mercado Pago, Kushki y Rapyd. Desbloquea flujos que los sandboxes oficiales rompen (como el 401 de Mercado Pago en sandbox PSE) y expone /v1/api para probar cobros por HTTP sin escribir código.

3.4 · Límites explícitos

Lo que el proyecto no hace

Dejar claros los límites ahorra dolores de cabeza antes de escribir una sola línea de código. Esto es lo que el SDK NO hace y por qué:

01

Los códigos de banco de PSE no son universales

Cada pasarela maneja su propia lista de bancos. En Mercado Pago, Bancolombia es 1007; en Rapyd es co_pse_bancolombia_bank. El SDK traduce PseBankCode.BANCOLOMBIA a cada formato nativo, pero los bancos disponibles dependen del catálogo activo de cada proveedor.

02

Los tokens de tarjeta no se cruzan entre pasarelas

Un token generado contra Wompi no sirve en Mercado Pago ni en Kushki. La tarjeta se tokeniza en el frontend (con kit-pagos-colombia/browser) contra la pasarela que tengas configurada para procesar ese cobro.

03

Solo tarjeta crédito/débito y transferencias PSE

Cubrimos los dos métodos que concentran la gran mayoría de transacciones digitales en Colombia. No soportamos pagos en efectivo (Efecty, Baloto), botones directos de billeteras ni dispersiones masivas.

04

La redirección de PSE sigue siendo obligatoria

En PSE el usuario tiene que ir sí o sí al portal de su banco. El SDK normaliza cómo solicitas el pago y cómo recibes la URL de retorno, pero la autorización bancaria sigue siendo un paso externo.

Sobre métricas de ahorro de tiempo: No publicamos cifras inventadas como "80% menos tiempo de integración". Esas métricas las mediremos con desarrolladores reales en las sesiones de prueba de la Fase 5 de la tesis.

Kit Pagos Colombia es nuestro proyecto de grado para optar al título de Ingeniero de Sistemas en la Pontificia Universidad Javeriana. Lo estructuramos con la metodología Design Science Research (DSR) para construir una solución funcional a un problema recurrente de la industria.

Cada decisión de diseño está soportada en ADRs en el repositorio, con pruebas automatizadas y límites de calidad de código: acoplamiento CBO ≤ 5, complejidad por clase WMC ≤ 20 (la suma de la complejidad ciclomática de sus métodos) y cobertura de pruebas ≥ 80%.

Autores: Andres Henao · Joan Orduz · Joshua Prieto · David Rodriguez
