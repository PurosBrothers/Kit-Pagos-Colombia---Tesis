# Matriz de Trazabilidad — Kit Pagos Colombia

> **Artefacto de proceso del Definition of Done (condición 5).** Esta matriz registra, para cada requisito funcional, su estado de implementación y la evidencia que lo sustenta: el issue que lo cerró, el PR que lo implementó y las pruebas que lo cubren. Es la *vista de proceso* de la trazabilidad.
>
> La *vista de arquitectura* —qué componente implementa cada requisito— vive en la [sección 5 de `layers-and-components.md`](../02-arquitectura/layers-and-components.md), con la que esta matriz se mantiene sincronizada por referencias cruzadas: esta matriz responde *¿está hecho?*, esa sección responde *¿con qué se hace?*.
>
> **Cómo se actualiza:** cualquier PR que implemente, modifique o cierre un requisito funcional debe actualizar la fila correspondiente de esta matriz **en el mismo PR** (estado, issue, PR y pruebas). El checklist de pull requests de [`CONTRIBUTING.md`](../../CONTRIBUTING.md) lo exige desde la creación de este artefacto.

## 1. Leyenda de columnas

| Columna | Qué significa | Criterio de verificación |
|---|---|---|
| **RF** | Identificador del requisito funcional (RF-01…RF-15), el mismo de la sección 5 de `layers-and-components.md` y del SRS | Coincide con la tabla de la sección 5 |
| **Requisito** | Nombre del requisito según el SRS | Coincide con la tabla de la sección 5 |
| **Componentes** | Componentes del SDK, de la API de Simulación o de la documentación que lo implementan | La vista de arquitectura (sección 5) es la fuente de esta columna |
| **Estado** | `Implementado`, `Parcial` o `Pendiente` | Un RF está `Implementado` si existe evidencia de issue, PR y pruebas; `Parcial` si falta alguna de las tres; `Pendiente` si todavía no hay trabajo cerrado |
| **Issue(s)** | Número(s) del issue que lo rastreó o cerró | Enlace al issue en GitHub |
| **PR(s)** | Número(s) del pull request que lo implementó | Enlace al PR en GitHub |
| **Pruebas** | La suite o el archivo de prueba que lo cubre | Debe poder ejecutarse (`npx jest`, `npm run test:sandbox`, `npm run typecheck`) |

## 3. Cómo verificar la matriz

Nada de lo anterior es declarativo: cada columna tiene que poder comprobarse.

1. **Estado ↔ issue:** cada RF `Implementado` tiene al menos un issue cerrado enlazado. Los `#` son enlaces vivos; un enlace roto es un hallazgo.
2. **Issue ↔ PR:** el PR de una fila aparece como "mergeado" en GitHub (`merged_at` no vacío). La mayoría de los PRs de este proyecto se mergean a `devops`, así que los issues se cierran a mano con el comentario de cierre enlazando el PR.
3. **PR ↔ pruebas:** para un RF con pruebas automatizadas:
   ```bash
   cd sdk && npx jest            # pruebas unitarias del SDK
   cd simulator-api && npx jest  # suites de la API de Simulación
   cd sdk && npm run test:sandbox # pruebas de contrato contra los sandboxes reales
   cd examples && npm run typecheck # los ejemplos contra la superficie pública del SDK
   ```
4. **Fila nueva:** cuando un PR abre una fila nueva (por ejemplo, una iteración posterior agrega un RF), debe traer issue, PR y pruebas en el mismo PR que la crea; una fila sin los tres no se considera `Implementado`.

## 4. Notas de trazabilidad

- El renombrado `SdkError` → `KitPagosError` está cerrado por el issue [#62](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/62): la jerarquía de errores vigente es `KitPagosError` + `KitPagosErrorCode`. La sección 5 de `layers-and-components.md` todavía cita `SdkError` en la fila RF-05; esa desincronización de la vista de arquitectura se corrige bajo el issue [#66](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/66), no en esta matriz.
- El issue [#124](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/124) no cambia el estado de ningún RF: cierra el **comportamiento** de la API de Simulación, no un requisito. Lo que aporta es que el estado de un cobro pasó de estar repartido entre las factorías y los routers a estar en las tablas de `simulator-api/src/state/`, con tres propiedades que las pruebas nuevas verifican: el escenario se fija en la creación y las consultas no lo alteran, una consulta responde el registro guardado en vez de fabricar uno, y las fallas técnicas no crean ni mutan estado. El RF-01 y el RF-03 ganan esa columna de componentes; el alcance del RF-10 —que los escenarios se alcancen desde el SDK— lo resolvió después [#122](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/122).
- Los RF-10, RF-12 y RF-13 no están completos (revisado el 6 de octubre de 2026). El RF-10 es parcial: [#65](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/65) dejó los escenarios en `/v1/sim` (PR [#97](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/pull/97)), y [#122](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/122) los hace alcanzables desde el SDK sin cabeceras (punto 83 del `architecture-log.md`); lo que falta está en su fila. El RF-12, bloque 1 de [#130](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/130), quedó implementado dentro de [#122](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/122) y pasa a `Implementado` cuando ese PR se integre. El RF-13 sigue en [#105](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/105), [#106](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/106) y [#107](https://github.com/PurosBrothers/Kit-Pagos-Colombia---Tesis/issues/107), diseñado en la sección 3.6 de `layers-and-components.md` y sin código en `simulator-api/src`.
- Esta matriz es un artefacto de proceso exigido por la condición 5 del Definition of Done (`docs/project-management/methodology.md`) y por el control de cambios de la sección 7 del mismo documento.
- **Los objetivos específicos de la tesis viven aparte**, en [`thesis-objectives.md`](thesis-objectives.md), y se relacionan con esta matriz por referencias cruzadas: cada objetivo lista los RFs que aportan su evidencia (sección 2 de ese documento) y este nivel de la matriz responde *¿está hecho?* mientras esa sección responde *¿qué objetivo de la tesis cumple?*. No se integran aquí porque un objetivo no tiene issue, PR ni pruebas por fila, y esta matriz es un artefacto del DoD con columnas fijas.
